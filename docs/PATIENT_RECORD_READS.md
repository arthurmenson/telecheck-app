# Patient record reads

Authenticated patients can read persisted consultation history at `GET /v1/async-consults` and their own medication list/detail at the existing `/v0/pharmacy/patients/:patientId/prescriptions` and `/v0/pharmacy/prescriptions/:id` paths. These capabilities do not establish a completed prescribing, payment, refill or dispensing workflow.

History accepts `limit` (default25, maximum100) and `offset` (default0, maximum10000), returning `rows`, `limit`, `offset`, and `has_more`. It uses the patient summary view, a patient ownership predicate and stable creation-time/ID ordering. The exact bound nonce, owned session, active patient account and tenant are checked before and after the read using database wall-clock expiry. Its own database transaction must use READ COMMITTED so the final check sees committed revocation. The private assertion owner has only the required identity/context column privileges; it cannot read clinical tables and is not assumable by application roles. Only the existing patient reader role can call this assertion.

Medication list accepts the existing eight stored status values and a positive integer `limit` (default50, clamped to500). Unknown or repeated query parameters are rejected. Detail returns a tenant-blind404 for absent, malformed, foreign-patient or foreign-tenant record IDs. All these reads use `Cache-Control: no-store`. Infrastructure errors remain errors, never fabricated empty lists.

The medication response is exactly `id`, `medication_name`, `strength`, `formulation`, `dose_instructions`, `quantity`, `quantity_unit`, `refills_allowed`, `status`, `prescribed_at`, `activated_at`, and `expires_at`. `refills_allowed` is the prescribed maximum, not remaining entitlement. Internal notes, indication, patient/tenant/clinician identifiers, protocol and interaction metadata are omitted. Existing write-response contracts are unchanged.

Migration087 introduces `pharmacy_patient_reader` as a NOLOGIN/NOINHERIT slice capability. Application transactions explicitly assume it. Its only protected operation is the read wrapper; neither it nor ordinary application SQL gets raw medication-table access. The separate, unassumable SECURITY DEFINER owner has only required column reads, uses forced tenant RLS and qualified objects, and checks the bound nonce, exact session, active nondeleted patient account, current country and active tenant. It rechecks after buffering results and rejects stronger isolation without changing it. The HTTP repository bounds statement and lock waits to5seconds and2seconds. The rollback removes only this capability and preserves records.

Run `npm run verify:patient-reads` against an isolated, fully migrated loopback database. Set `NODE_ENV=development`, `AUTH_DEV_OTP_ECHO=true`, `EMAIL_PROVIDER=noop`, `SMS_PROVIDER=noop`, and the standard app, Identity and binder connection URLs with their actual restricted LOGIN roles. Set `PATIENT_READ_ACCEPTANCE_ADMIN_DATABASE_URL` to the migration connection for the same isolated database, plus the normal development JWT/Redis configuration. The script registers synthetic accounts through real HTTP, verifies both countries, seeds explicitly synthetic medication and consultation metadata rows for read testing, and exercises projection, raw-table/owner denial, nonce/isolation failures, schema shadows, concurrent deletion/revocation and session/nonce expiry during blocked reads. It retains synthetic account/audit/fixture records and prints no credentials. It is not a payment, prescribing or clinical journey acceptance test.

The general test suite serializes files using Vitest's supported `fileParallelism: false` setting because the shared database fixture holds transaction-scoped audit locks. The former `forks.singleFork` object was ignored by the installed Vitest4 runtime. Test isolation and assertions remain enabled.

The module readiness endpoint reports503 until the full pharmacy write, refill/dispensing and provider journeys pass acceptance. This does not disable the independently usable patient read routes. Legacy medication clinical fields still require the separate classified-encryption migration; no encryption-at-rest claim is made by this read repair.
