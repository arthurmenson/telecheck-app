# Patient session refresh candidate

This increment renews access for active patient and delegate accounts. It is an author candidate requiring a fresh independent review before release. It does not replace the separate staff authentication protocol.

`POST /v0/identity/sessions/refresh` accepts only `{ "refresh_token": "..." }` and requires a canonical uppercase ULID `Idempotency-Key`. Authentication comes from the opaque body credential. A supplied or expired access bearer does not change the operation's authority or cache owner.

A successful response contains only `session`, `access_token`, and `refresh_token`. The session projection contains `session_id`, `account_id`, `created_at`, `last_active_at`, and `expires_at`, with UTC timestamps in millisecond ISO format. The same device session receives a newly generated refresh credential and a new 15-minute access JWT. Rotation preserves the original session expiry, including any stricter stored deadline. It does not extend the session's absolute lifetime. A delegate refresh receives only their own account's patient-role token; caller-supplied delegated or staff authority is rejected.

Clients must persist an attempt key with the original opaque credential before sending and adopt both replacement credentials atomically. An uncertain request must retry with exactly the same key and body. The private Identity receipt is recoverable for at most 900 seconds and only while its exact successor is still current, its actual account and session remain live, and the signed access receipt remains valid. A further rotation, logout, reset, account-state change, or expiry invalidates credential replay. Account and session locks serialize refresh with PIN reset and logout. Wall-clock checks run after lock waits. The mutation, required audit, domain event, and private receipt commit together before success is returned.

Invalid or expired credentials return `401 identity.session.invalid_or_expired`; invalid input returns `400 internal.request.invalid`; a changed body under the same key returns `409 internal.idempotency.body_mismatch`; an in-flight request returns `409 internal.idempotency.in_flight`; database or uncertain commit failures return a generic `503 identity.authentication.unavailable`. Refresh and logout responses carry `Cache-Control: no-store`. Clients must retain the original attempt on an ambiguous failure instead of silently creating another key.

Logout accepts the existing `refresh_token` plus an optional `refresh_idempotency_key`. The exact original token and a still-live private receipt can revoke the same device session after a lost refresh response, including after a later rotation. The server derives the session from the receipt and verifies its signed identity; the client cannot select an arbitrary session. Unknown credentials retain the existing neutral logout response.

Logout is a separate revoke-only operation. A current opaque credential can revoke its owned session for every existing account type, including legacy staff, without requiring an active or nondeleted account. A valid pending-refresh logout receipt can also revoke after account suspension, archival, deletion, or classification changes. Both paths retain account-before-session locks, exact tenant/session ownership, and after-wait session/receipt expiry checks. They never issue credentials or relax active patient/delegate eligibility for refresh or credential replay. Repeated logout emits no duplicate revocation evidence, and account restoration cannot revive the revoked session.

There is an explicit bounded limitation: if a refresh commits but the response is lost, and the client does not resolve the attempt within 900 seconds, the original credential and expired receipt cannot revoke the unknown successor. The client can sign out locally and must require genuine sign-in on next use, but it cannot claim acknowledged server revocation in that case. The original absolute session deadline still applies. This candidate retains hard receipt expiry and purge behavior. A future separately reviewed migration must add durable, session-bound, hashed original-token lineage usable only to revoke the same session; it must not preserve plaintext credentials or permit access recovery beyond the receipt window.

The disposable author verifier is `scripts/verify-patient-refresh-runtime.mjs`. This revised candidate accepts only the isolated local PostgreSQL port 56597 and test database, using separately supplied private fixture connection credentials. The earlier candidate's source, port56589 profile, and evidence remain preserved. The preparation script changes roles only in the new isolated cluster and registers real synthetic accounts through the actual API. The verifier uses real Fastify HTTP, dedicated Identity and binder connections, and genuine issued tokens. Its staff-negative cases use the actual legacy phone-OTP issuer after classifying isolated synthetic accounts; they do not establish governed staff MFA acceptance. No token or session row is fabricated. Selected existing synthetic rows and test-only triggers are changed to exercise expiry, concurrency, and transaction failure boundaries.

The natural-expiry fixture must be prepared once and retained for at least 15 minutes. With `PATIENT_REFRESH_NATURAL_EXPIRY=true`, the verifier checks that the original actual access JWT has naturally expired and the actual refresh credential still yields a usable replacement. That consumes the original fixture credential, so preserve its result rather than rerunning it with a new key.

No migration is added. Author runtime verification targets the existing migration 097 schema. All private receipt storage and session primitives are already present there; this change does not require the unrelated clinician enrollment migration 098 or staff and care candidates 099–103.
