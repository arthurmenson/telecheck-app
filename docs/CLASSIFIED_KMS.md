# Classified tenant encryption

The normal service API in `src/lib/classified-kms.ts` implements three-tier encryption, versioned reads and durable decrypt evidence. It requires migrations 084–086, a committed tenant key binding, an authenticated SI-010 session and `KMS_DATABASE_URL` authenticating directly as `kms_service_role`. Ordinary `telecheck_app_role` cannot become that role or write the keyring. Generic `kmsEncrypt`/`kmsDecrypt` remain gated; old envelopes do not automatically become trusted records.

Authorize the resource and patient/assignment/consent first. Call encryption or decryption **before** taking audit/keyring advisory locks in the business transaction; the engine enforces that ordering. Use a server-selected descriptor `{dataClass, patientId, resourceType, resourceId, field}`. Mixed clinical free text uses `pii_sensitive_clinical`. Do not derive a descriptor from arbitrary request fields or expose a general encrypt/decrypt HTTP endpoint. Patient sessions are restricted to their own scope; platform-admin cross-tenant and delegate flows remain closed pending their explicit authorization integrations.

Protected tables/functions/catalogs are schema-qualified and dedicated transactions pin their search path. Temporary objects and caller search paths cannot replace the registry or context helpers. Live checks require `accounts.deleted_at IS NULL` as well as active account/session state, including revalidation after provider calls and before independent audit COMMIT. A still-attributable request nonce may record denial evidence after the account is deleted; it cannot authorize key use.

The physical business transaction must use **READ COMMITTED**. The engine checks its actual isolation before actor/key/provider work and again during post-provider validation; REPEATABLE READ, SERIALIZABLE and other unsupported settings fail closed without changing the caller's transaction. The caller owns transaction setup and cleanup. Independent keyring/audit transactions explicitly begin at READ COMMITTED, overriding connection defaults before any transaction snapshot. Each later actor SELECT therefore sees committed deletion/revocation, including changes made while the provider or audit INSERT was in progress. A plain `BEGIN` works when the business connection's default is READ COMMITTED; configure it explicitly if deployment defaults differ.

`encryptClassified(tx, descriptor, Buffer)` returns migration 056's `{ciphertext, dekId, iv, tag, alg, algVersion, aad, encryptedAt}`. `decryptClassified(tx, descriptor, envelope)` returns bytes only after a separate audit transaction commits. `rotateClassifiedWriteVersion(tx, descriptor)` requires a tenant administrator and an existing version. It advances the active write version and records incomplete historical rewrap; old versions stay readable and cannot be retired/purged. It does not emit rotation-completed evidence.

TCROW002 contains a fresh row key wrapped under the class DEK plus payload ciphertext. External IV/tag authenticate payload; canonical AAD authenticates tenant, class, patient, resource type/ID, field, key version, algorithm and timestamp. KMS wraps class keys with exactly `{tenant_id,data_class}`. Returned AWS key ARN and symmetric algorithm are checked. Patient/resource IDs appear only in local AAD/audit, never AWS context/tags/session names. Secrets and SQL/AWS diagnostics do not enter public errors.

There is no plaintext-key cache and no application STS credential cache (capacity zero). Admission defaults to four concurrent operations, with no unbounded queue; the dedicated KMS pool has two connections and a two-second acquisition deadline. AWS requests have a five-second default deadline; audit lock and statement limits are one and five seconds. Raw class keys and row keys are erased after use. Provisional plaintext is erased on authentication, context or audit failure. Returned plaintext belongs to the authorized caller, who must avoid logging it and erase temporary buffers when practical.

Client-side database deadlines are two seconds per query and eight seconds per independent transaction, including the initial role check, COMMIT and rollback cleanup. They do not depend on receiving the server's timeout reply. An uncertain/timed-out dedicated connection is discarded and never reused; late query/acquisition replies cannot resume the request. Caller-side KMS queries also have deadlines and require a physical pg client with `end()` cancellation, as supplied by `withTransaction`. On timeout KMS closes that client without consuming the transaction owner's `release()`. Adapters that cannot cancel fail closed. Keys and provisional plaintext are erased before failure auditing, and a recovered connection/request can use the released capacity.

Every lookup emits Cat C `kms.dek_lookup`; every successful decrypt emits Cat A `kms.decrypt_invoked`; every attributable failure attempts a durable Cat A `kms.decrypt_failed`. Success is impossible if audit INSERT/COMMIT fails. Missing/expired caller context cannot forge actor attribution and fails closed before KMS. Initial provisioning adds Cat A `kms.dek_created`, a counsel-approved contract extension, instead of mislabeling first creation as rotation. Initial policy audits all successful operations (stricter than canonical lower-class 1% sampling); sensitive/financial/audit classes and failures remain permanently 100%.

If required auditing cannot complete, the boundary emits the fixed operational event `kms.audit.unavailable`, aggregated to at most once per process per minute. It contains no error details, nonces, tenant/patient/resource identifiers, ciphertext or keys. This operational signal reports lost audit availability; it does not replace durable evidence or permit plaintext release, and it never recursively retries auditing.

## Provisioning and verification

1. Apply the reviewed migrations as the migration principal. Provision a unique credential for the dedicated `kms_service_role` login; never grant membership to the app role. Configure `KMS_DATABASE_URL` through the secret store. The dedicated pool requires verified TLS when `DATABASE_SSL_MODE=require`.
2. Review and deploy `infra/kms/tenant-primary.template.json` **only in us-east-1**, once per tenant. Use the actual application workload role and a separate key administration role. The template preserves key resources on deletion/replacement and enables annual automatic rotation. Deploy under the key administrator role with the permissions required by CloudFormation; AWS requires the creating principal to retain PutKeyPolicy access. The template keeps the policy-lockout safety check enabled. It does not activate a replica, DR or break-glass broker.
3. Give the application workload role `sts:AssumeRole` and `sts:TagSession` on the specific generated service role, with `aws:RequestTag/tenant_id` fixed to the tenant and `aws:TagKeys` restricted to `tenant_id`. No SourceIdentity is sent, so no unconfigured `sts:SetSourceIdentity` dependency exists.
4. As an operator authorized to assume `kms_provisioner_role`, insert the immutable output CMK ARN/role ARN into `tenant_kms_bindings`, with `primary_region='us-east-1'`, `residency_policy='us_only'` and NULL replica. Never insert aliases or invented ARNs. A `us_with_dr_fallback` binding requires an independently provisioned same-material MRK replica in us-west-2, but runtime remains pinned to primary until the separate DR readiness workflow is implemented. No defaults manufacture a tenant binding.
5. In a provisioned AWS sandbox verify correct tenant/class success, wrong tenant/class/role/tag rejection, returned KeyId identity, CloudTrail context, encryption/decryption availability and durable audit rollback/failure behavior. This repository's controlled AWS transports verify application contracts; they are **not live AWS policy evidence**.

Full DR override/canary/policy verification, emergency break-glass broker, immutable historical rewrap projections and verified retirement/purge remain separate completion work. The new API does not enable those paths. Local synthetic workflows need an explicitly separate, synthetic-only deployment profile; setting NODE_ENV=test is not a production activation mechanism.

Run `npm run test:kms` against a freshly migrated database named with `classified_kms`, using `KMS_INTEGRATION_DATABASE_URL` for the administrative fixture connection. The test uses real role/session authorization and separate physical connections, with controlled AWS transport only. The dedicated CI job runs the full migration chain before these tests. Rollback scripts refuse when registry/keyring rows exist, so a rollback cannot strand encrypted records. The application shutdown hook should call `closeClassifiedKmsPool()` after requests drain.

Official APIs used: [AssumeRole](https://docs.aws.amazon.com/STS/latest/APIReference/API_AssumeRole.html), [GenerateDataKey](https://docs.aws.amazon.com/kms/latest/APIReference/API_GenerateDataKey.html), [Decrypt](https://docs.aws.amazon.com/kms/latest/APIReference/API_Decrypt.html). The implementation corrects canonical pseudocode's `sts:RequestTag` to `aws:RequestTag` and uses actual `EnableKeyRotation`/`RotateKeyOnDemand` APIs. `DescribeKey` is separately authorized because it does not accept encryption context.
